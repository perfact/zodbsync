# Layering rule is warn-only; prune removes subtrees across layers

A layer should only contribute a child object under a parent that it defines itself, or that is defined in a layer further down the stack (lower priority, i.e. a lower config file prefix such as `00-`). The intended stack is a toolkit layer at the bottom that defines everything up to and including `__root__/__meta__`, with customer layers above it overriding properties and adding children. `record` and `watch` log a warning when an object is placed in a layer below the lowest layer that defines its parent. They do not refuse or reroute: the rule is an intention, and enforcing it would break existing setups and `zodbsync move` workflows before we know whether we want that.

The comparison uses the lowest layer defining the parent, not the topmost. A customer layer that overrides a parent's `__meta__` sits above the base layer's children; those children are still correctly placed. There is no exemption for top-level objects: the lowest layer is expected to define the root, so a setup without it warns for every top-level object contributed by a named layer.

Overriding a parent in a higher layer makes its children in the lower layer into layer boundaries (ADR 0004). That is intended, not noise: the children must carry an explicit `zodbsync_layer`, otherwise they would acquire the parent's layer and edits to them would land in the override layer instead of where they are defined. New children created under the overridden parent go to the override layer and may need to be moved with `zodbsync move`.

`fs_prune` follows the same model. When an object disappears from the ZODB, it checks in how many visible layers the object's own `__meta__` exists. If that is at most one, there is nothing to shadow, and the whole subtree is removed from every visible layer where the directory exists. This also removes descendants contributed by other layers (for example a child in the fallback layer under a parent that is defined only in a named layer), instead of leaving them behind with no parent. If `__meta__` exists in two or more layers, the top copy is removed and a `__deleted__` marker is placed there to shadow the lower ones, which stay untouched.

Cleaning up other layers' workdirs during `record` is acceptable because the ZODB is the source of truth and the object is gone entirely. A named layer's workdir is regenerated from its source by `layer-update` and is a git repository, so the removal is recoverable. `layer-update` itself still only writes the workdir of the layer being updated.
